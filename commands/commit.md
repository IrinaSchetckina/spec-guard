## Контекст

Гілка: !`git branch --show-current`

Статус: !`git status --short`

Staged-діф (знімок на момент виклику — після будь-якого `git add`/`git reset` він застарілий, див. крок 2): !`git diff --staged`

Unstaged-діф (лише статистика): !`git diff --stat`

Останні коміти (зразок стилю): !`git log --oneline -8`

## Завдання

Зроби **один атомарний коміт** зі змін вище. Підказка користувача про суть змін: $ARGUMENTS

### 1. Перевір, що йде в коміт

- Якщо staged порожній — додай доречні файли сам (`git add <шляхи>`), **ніколи не `git add -A` наосліп**.
- **Не комітити ніколи:** артефакти збірки й кешів, локальні конфіги з машинними шляхами,
  файли IDE та ОС, секрети/токени/ключі, дампи й логи. Якщо таке вже в staged — прибери через
  `git reset HEAD -- <шлях>` і скажи про це.
- Конкретний список сміття залежить від екосистеми — звір із `.gitignore` проєкту та його
  інструкціями (`AGENTS.md`/`CLAUDE.md`/`CONTRIBUTING.md`), а не з пам'яті.
- **Не все, що схоже на артефакт, ним є:** лок-файли залежностей (`*.lock`, `*-lock.json`,
  `*.lockb`, лок-файли менеджерів пакетів) комітити **треба** — це залочені версії, а не сміття.
  Якщо сумніваєшся щодо файла — `git check-ignore -v <шлях>` і подивись, що каже сам проєкт.
- Перечитай staged-діф на випадкові артефакти: закоментований код, `TODO` без контексту,
  налагоджувальні `print`/`console.log`, тимчасові файли, зайві правки форматування.

### 2. Після будь-якого `git add` — перечитай staged заново

Діф у розділі «Контекст» — це **знімок на момент виклику команди**. Щойно ти виконав `git add`,
`git reset HEAD -- <шлях>` або будь-що інше, що змінює індекс, цей знімок більше не описує коміт,
який ти збираєшся зробити.

Тому **обов'язково**:

```bash
git diff --staged
git status --short
```

і склади повідомлення **за фактично застейдженим вмістом**, а не за початковим знімком.
Це не формальність: інакше легко описати файли, яких у коміті немає, проґавити ті, що додалися,
або не помітити, що в індекс заїхало сміття з кроку 1.

Правило: **останній `git diff --staged` має бути виконаний після останньої зміни індексу
і до `git commit`.** Якщо між ними був хоч один `add`/`reset` — перечитай ще раз.

### 3. Атомарність

Один коміт = одна логічна зміна. Якщо в staged змішані незалежні речі (наприклад, рефакторинг
плюс нова фіча, або зміна коду плюс правка доків, не пов'язана з нею) — **не комічу все разом**:
розклади на кілька комітів через `git add <шляхи>` по черзі, або скажи користувачу, що саме варто
розділити, і запитай.

Коли комітів кілька — правило з кроку 2 діє для **кожного** з них окремо: застейджив наступну
порцію → перечитав `git diff --staged` → написав повідомлення саме під неї.

### 4. Повідомлення

Формат — Conventional Commits:

```
<type>(<scope>): <короткий imperative-заголовок>

<тіло: навіщо, а не що — лише якщо це не очевидно з діфу>

<трейлери>
```

- **type:** `feat:` (нова поведінка), `fix:` (виправлення бага), `chore:` (обслуговування,
  прибирання, залежності), `docs:` (документація), `test:` (лише тести), `refactor:` (зміна
  структури без зміни поведінки), `build:` (збірка), `ci:` (конвеєр).
- **scope** — модуль або компонент проєкту, коли це прояснює. Бери назви зі `git log` проєкту,
  не вигадуй свої. Без scope — теж нормально.
- **Заголовок:** англійською, imperative («add», «drop», «rename», не «added»/«adds»),
  з малої літери, без крапки в кінці, ≤ 72 символів.
- **Тіло** — англійською, пояснює **навіщо**: яку проблему знімає зміна, чому обрано саме такий
  шлях, що зламалося б без неї. Не переказуй диф. Якщо зміна тривіальна й самоочевидна —
  тіла не треба.
- Списком у тілі перелічуй лише те, що читач не побачить із заголовка.
- Згадуй тести рядком `Tests: <імена тестів>`, якщо коміт їх додає.
- Якщо в проєкті вже є свій стиль повідомлень (видно з `git log`) — тримайся його,
  а не цього шаблону.

### 5. Трейлери атрибуції

Якщо поточна сесія задає трейлери атрибуції (наприклад `Co-Authored-By:` і посилання на сесію) —
додай їх у кінці повідомлення після порожнього рядка, **точно в тому вигляді, який задано в
інструкціях цієї сесії**. **Не копіюй ідентифікатор сесії зі старих комітів** — він у кожної
сесії свій. Перевірити формат можна так: `git log -1 --format=%B`.

Комічу через heredoc, щоб зберегти багаторядковість:

```bash
git commit -m "$(cat <<'MSG'
feat(api): add GET /search backed by the upstream catalog

Clients go through this endpoint instead of calling the upstream directly.

<трейлери сесії, якщо вони задані>
MSG
)"
```

### 6. Після коміту

Покажи `git log --oneline -1` і `git status --short`. Якщо дерево не чисте — скажи, що лишилося
незакоміченим і чому.

### Чого не робити

- Не пушити (`git push`) — тільки якщо користувач прямо попросив.
- Не комітити в основну гілку (`main`/`master`) — працюємо через гілки. Якщо поточна гілка
  основна, спершу спитай.
- Не робити `git commit -a` і `git add -A` без розбору.
- Не використовувати `--no-verify`, не змінювати вже опубліковані коміти без прямого прохання.
